4-System Architecture & Computational Stress Scaling

High-performance geospatial architecture distributed across the four provided systems. The exact same full-featured backend engine runs on Sys 2, Sys 3, and Sys 4 as identical worker replicas, orchestrated by the Sys 1 client interface for load balancing, stress mitigation, and fault-tolerant failover:

Sys 1 Client Web-GIS & Cluster Orchestrator (Client Browser)

Interactive Web-GIS frontend interface. Manages satellite map land area selection, coordinate parsing, dynamic KML contour generation, client-side round-robin load distribution across worker replicas, and multi-layer GeoJSON visualization.

Sys 2 (Port 5246) Backend Compute Worker Replica 1 (Full Hydrological Engine)

Runs the full Python Flask REST backend pipeline: KML contour parsing, Bicubic DEM rasterization, D8 flow routing, river floodway exclusion, reverse-BFS catchment delineation, and Open-Meteo rainfall runoff sizing.

  • Endpoint: http://10.1.75.79:5246/analyzeContour
  • Capacity: Handles concurrent raster grid interpolations ($50\times50$ to $300\times300$).
Sys 3 (Port 5247) Backend Compute Worker Replica 2 (Full Hydrological Engine)

Identical backend worker instance providing parallel computational capacity. Relieves memory and CPU stress when processing large watersheds or high contour density datasets.

  • Endpoint: http://10.1.75.79:5247/analyzeContour
  • Failover Role: Automatically receives queued queries if Sys 2 is under peak load or offline.
Sys 4 (Port 5248) Backend Compute Worker Replica 3 (Full Hydrological Engine)

Identical backend worker instance completing the 3-node compute cluster. Ensures high system availability, sub-1.5s interactive response times, and resilience against single-point-of-failure bottlenecks.

  • Horizontal Scaling: Triples system throughput across independent worker processes.
